# 03 数据模型草案（先定关系，按任务分批建表）

## A. 当前已实现
- 使用 Django 自带 User、Group、Permission。
- `UserProfile(user[1:1], role, department)` 已实现最简角色标记；它**不是**对象级权限的完整实现。
- 其他 Apps 目前仅为占位目录。

## B. 候选业务实体与最小字段

| 实体 | 字段（除主键外） | 关系 |
|---|---|---|
| Customer | code、name、industry、owner、status、notes、时间戳 | 1:N Contact、1:N Inquiry |
| Contact | customer、name、position、phone、email、notes | N:1 Customer；敏感字段限制授权 |
| Inquiry | code、customer、title、source、description、status、owner、next_follow_up、时间戳 | N:1 Customer |
| Opportunity | code、customer、title、stage、estimated_amount、owner、expected_close_at | N:1 Customer；可关联 N:M Inquiry |
| FollowUp | inquiry 或 opportunity、author、occurred_at、summary、next_action | 对象活动日志，不等于审计日志 |
| TechnicalReview | code、inquiry、requester、assignee、due_at、status、question、conclusion、risk | 一次询盘 1:N 评估 |
| Requirement | code、title、description、type、priority、status、business_owner、technical_owner、acceptance_criteria | 客户来源 N:M Inquiry；项目 N:M |
| Product | code、name、owner、lifecycle_state | 1:N ProductVersion |
| ProductVersion | product、version、planned_release_at、status | unique(product,version) |
| Project | code、name、type、owner、planned_start、planned_end、status、product(可空) | 1:N Milestone、1:N WorkItem |
| Milestone | project、title、kind、planned_at、actual_at、status | N:1 Project |
| WorkItem | code、title、type、status、priority、owner、due_at、project(可空)、description | N:M Requirement（关联表） |
| Comment | target_type、target_id、author、content、时间戳 | 权限需基于目标对象检查 |
| Attachment | target、path、name、size、mime、uploaded_by | 文件读取必须鉴权，不能直接公网暴露 |
| ActivityLog | actor、target、action、before、after、reason、occurred_at | 业务活动历史，关键记录不可由普通用户修改 |
| AIJob | workflow_key、target、requested_by、status、started_at、finished_at、error_code | 可追踪 AI 异步任务 |
| AIResult | job、schema_version、result_json、reviewed_by、confirmed_at | 区分草稿与确认后的正式写入 |

## C. 关联关系
- Customer 1→N Inquiry；Inquiry 1→N TechnicalReview。
- Inquiry N↔M Requirement；Requirement N↔M WorkItem；Requirement N↔M Project（有必要时使用显式关联表保存来源、时间和备注）。
- Product 1→N ProductVersion；Project 可指向某产品或产品版本，但定制项目可以独立存在。
- WorkItem 可以独立存在（例如行政工作），也可以归属一个项目。

## D. 强制约束
1. **主键与业务编号分离**：id 可用 bigint；code 设置 UNIQUE。编号要考虑并发和年度跨年，不使用 `count()+1`。
2. **时间与责任**：所有核心表应包含 `created_at`、`updated_at`、`created_by`、`owner`（如适用）。
3. **重要业务对象状态**：使用 `TextChoices`，严格限制非法转移。
4. **安全**：删除关系时优先 PROTECT / SET_NULL，避免历史技术评估被一并删除。
5. **可查询性**：统计字段采用实体列、外键和索引；JSON 字段只保存非关键的 AI 草稿和附加信息。
6. **完整历史**：负责人与交付日期变更需要 before/after、操作者、时间和原因。
7. **并发**：业务编号分配、状态变更和审批使用事务与必要的行锁；同一提交可幂等去重。
8. **数据迁移**：每次变更模型都生成迁移，并测试从空库安装和从旧库升级。
9. **数据质量**：联系人、商机金额、AI 文本在展示和日志层按权限脱敏。

## E. 设计暂不冻结的部分
- 商机与询盘是一对多还是多对多；第 01 任务由市场负责人确认。
- 是否允许研发成员兼任市场支持角色；第 02 任务验证角色组合需求。
- 正式产品需求的多来源合并机制；第 03 任务结合实际案例确定。
