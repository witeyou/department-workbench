# 02 核心业务流程与状态机

> 状态值为建议英文存储枚举。Codex 建模前如需改动，必须同步更新本文件、迁移和状态测试。

## A. 询盘 Inquiry
`new → qualified → following → won/lost/closed`；对暂时无法确认的询盘允许标记 `on_hold`，并记录原因及下一跟进时间。
- 市场人员：创建、补充信息、跟进；跨负责人改派需市场负责人权限。
- 关闭必须填写关闭原因；已经产生的技术评估记录不允许级联删除。
- 询盘可以关联多个技术评估和一个或多个商机（是否多商机由市场负责人最终确认）。

## B. 售前技术评估 TechnicalReview
`requested → assigned → evaluating → answered → acknowledged → closed`
异常分支：`requested/assigned/evaluating → needs_info → evaluating`；允许申请人撤回未开始的请求 `requested → cancelled`。
- 市场提交时需描述背景、问题、期望答复日期、关联询盘。
- 研发负责人指派评估人；评估人提交结论（支持/部分支持/不支持/待进一步确认）、建议方案和风险。
- 市场需确认已收到结果；评估“已答复”不代表客户接受、研发立项、合同承诺。
- 评估超期按申请承诺的 SLA 或明确答复截止时间判断，计时规则须可配置。

## C. 统一需求 Requirement
`draft → triage → review → decision`，再分支：
- `decision → accepted → planned → developing → verifying → delivered → closed`
- `decision → deferred`，后续可重新进入 `review`。
- `decision → rejected → closed`。
规则：需求归属与技术评估要分开；变更优先级、目标版本、验收条件记录历史。需求接受由授权决策人确认，不由 AI 执行。

## D. 产品与项目
- 产品 Product：稳定产品主档；版本 ProductVersion：版本标识、状态、计划发布日期。
- 项目 Project：`proposed → active → paused → completed/terminated`；类型 `product_rd` / `custom_delivery`。
- 里程碑 Milestone：名称、计划/实际日期、结果、阶段类型。对正式产品可选择：立项、输入、方案、β、Release、定型；定制项目使用通用计划节点。
- 项目进度至少展现任务完成率、里程碑完成情况和项目负责人主观确认进度（明确区别）。

## E. 工作任务 WorkItem
`todo → in_progress → done`，分支 `in_progress → blocked → in_progress`、`todo/in_progress → cancelled`，需要复工则 `done → in_progress` 并记录理由。
- 任务至少有：标题、类型、所属项目（可为空，用于跨组任务）、负责人、优先级、截止日期、状态。
- 任务完成需要有处理结果；任务延期需能在报表里查询到，不应修改截止日期掩盖延期历史。

## F. 端到端事件样例
1. 市场创建 `INQ-2026-0001` 并关联客户。
2. 发现客户需要一个未确认支持的功能，申请 `TR-2026-0001`。
3. 研发负责人分配评估人；评估人答复并留存附件。
4. 市场确认答复，必要时提取 `REQ-2026-0001`。
5. 需求负责人决定接受/暂缓/拒绝；接受后进入产品计划或定制项目。
6. 负责人将需求关联项目里程碑和工作任务。
7. 每次推进都形成 ActivityLog，领导按权限下钻明细。

## G. 人员责任与审批原则
- 创建者、当前负责人、审批人是独立字段；操作员不一定是负责人。
- 人工审批必须有明确角色；所有审批需记录审阅人、时间和结论。
- 业务状态变更由 Django service 层显式函数完成，事务内校验当前状态和对象授权。
- AI 不得直接改变 `accepted`、`completed`、`delivered` 或评审通过等关键状态。
