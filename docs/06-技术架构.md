# 06 技术架构与系统边界

## 技术栈
- Python 3.12、Django 5.2 LTS（单体应用）；Django Templates + HTMX（需要时）+ Bootstrap 本地资源 + ECharts（后续）。
- PostgreSQL（生产），SQLite（本机快速验证）；uv、pytest、ruff、GitLab CI。
- Docker Compose：Nginx、Django、PostgreSQL；Dify 在独立部署中通过 API 调用。
- 后续确实需要定时/高耗时任务再引入 Redis + Celery，不提前分布式化。

## 模块边界
`market` 存客户询盘商机；`requirements` 存跨部门评估、需求及决策；`products` 存产品/版本；`projects` 存项目/里程碑；`tasks` 存任务；`dashboard` 提供有授权的汇总；`ai` 管 Dify 接口及结果草稿；`accounts` 存角色与业务范围。

跨模块操作通过显式 service 层组织数据库事务。视图不应该绕过业务服务更新状态。当前 `apps/*/models.py` 为空是刻意设计，待相关任务卡进行建模。

## API 与 AI
业务操作先服务内部模板使用；AI 接口与后续外部系统复用相同服务层。输入输出 Schema 要有版本号；Dify 令牌只保存在后端环境变量；请求/响应脱敏日志；重试必须考虑幂等。

## 数据源原则
PostgreSQL 是业务事实来源；AI 向量索引、知识库结果、缓存不得反向替代正式状态。领导面板使用授权后的 ORM 聚合查询，AI 负责解释而不计算原始事实。

## 部署与风险
- `.env` 仅本机维护，绝不提交。
- 演示 Compose 暂无 HTTPS、备份、文件鉴权或反滥用限制，不能暴露公网。
- 代理部署时校验 `ALLOWED_HOSTS`、可信 Origin、TLS Header；配置 SECURE Cookie 与 CSRF 保护。
- 不同角色访问客户附件和历史记录需要单独鉴权。
- PostgreSQL 需逻辑备份、附件备份、恢复演练、监控告警和容量计划。
- 生产必须独立记录错误日志、结构化审计和应用版本。
