# 01 产品范围 / V0.1–V1.0 需求基线

## 1. 业务目标
服务 20–30 人部门，覆盖市场小组、研发小组与领导；通过单一 Web 工作台统一记录询盘、跨组评估、需求、项目、任务和关键风险。减少口头流转、重复填表和人工周报。部署于内网，未来集成 Dify，但业务系统不得依赖 Dify 可用性。

## 2. 用户与职责
- 市场人员：登记客户/询盘、跟进商机、申请售前技术评估、获取反馈。
- 市场负责人：分派询盘、处理商机、批准向研发发起正式请求。
- 研发人员：完成评估、执行任务、记录风险和处理结果。
- 研发负责人：分配技术资源、审核评估、维护项目计划。
- 测试人员：验收任务与需求结果。
- 部门领导：关注统计、超期和待决策事项；可查看授权范围内明细。
- 系统管理员：账号、配置、审计；**不因管理员职务当然获得所有商业数据查看许可**（初版后台管理员需谨慎指定）。

## 3. 必须支持的业务
- **市场**：客户、联系人、询盘、商机及跟进活动记录；询盘与商机可关联但不是同一个实体。
- **协同**：询盘产生技术评估申请；指派、接受、退回补充资料、提交结论；市场及时获得结论。
- **需求**：来源、分类、优先级、接受/暂缓/拒绝决策、验收条件、产品和项目关联；支持同一产品需求来源于多个客户。
- **研发**：产品、产品版本；内部产品研发项目和客户定制项目；任务、负责人、截止时间、阻塞状态、里程碑。
- **管理**：数据统计可下钻、超期标记、决策待办与操作审计。
- **AI（后续）**：询盘结构化、需求分析、任务草稿、项目摘要；人工确认后才能更新正式数据。

## 4. 关键业务约束
- 询盘不自动等于研发需求；售前技术评估结论不自动构成项目立项或交付承诺。
- 客户定制与产品版本研发分别可追踪，但使用统一任务基本模型。
- 商机金额与报价等商业敏感字段应权限隔离。
- 需求可能 1→N 任务，客户来源可能 N→1 产品需求，不能强行固定树状父子关系。
- 系统须保存谁在何时为何改变状态、负责人、计划交付时间和评估结论。
- 业务历史数据原则上不可直接物理删除；必要时匿名化归档须经过授权流程。

## 5. 非目标（不进入 V1.0）
财务/发票管理、销售漏斗预测算法、复杂工时核算、PLM 文件管理替代、通用 BPM 设计器、通用报表搭建器、手机原生 App、自由 SQL 智能体、跨平台即时通讯抓取、实时多人协同编辑。

## 6. V0.1 最小闭环
客户登记 → 创建询盘 → 发起技术评估 → 研发回复 → 市场确认收到 → 负责人查询超期/处理中记录。先打通这条链路，再扩展完整产品项目管理。
